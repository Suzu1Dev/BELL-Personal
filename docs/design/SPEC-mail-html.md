# BELL Personal — addendum: a mail's original layout and its images

Date: 2026-10-15. Owner: design and tech lead. Status: **built** (see `docs/STATUS.md` 「Mail original layout and images」).

This addendum extends `docs/design/SPEC-ux.md` and `docs/design/SPEC-mail-assignments.md` for one request from the owner:

> 信件有辦法顯示圖片嗎？在保持安全性的同時

The owner then chose:

1. **顯示方式 = 原始版面（沙盒）.** The reader shows the mail's own HTML layout and images, sanitized on the server, inside a sandboxed frame that can run no script and cannot reach the app. A mail without HTML shows its plain text as before. The reader has a 原始版面 / 純文字 switch, and the choice is remembered.
2. **外部圖片 = 按一下才載入.** Remote images are not loaded until asked. A calm notice 「已封鎖外部圖片，保護你的隱私。 [顯示圖片] [一律顯示「寄件者」的圖片]」 loads them **through the owner's own server** (the sender never sees the owner's device or browser; see D8 for what it does see); known tracking pixels are never loaded. A per-sender trust list (address or domain) is editable in 連線與設定 › 資料與隱私. Inline (`cid:`) images and image attachments come from Gmail itself and are always shown.

Where this file is silent, SPEC-ux and SPEC-mail-assignments apply. Every override is listed in §0.2. The server contract is `docs/ARCHITECTURE.md` §10.11.

## 0. Decision record

### 0.1 Decisions (security-relevant ones first)

| # | Decision | Why (and what was rejected) |
|---|---|---|
| D1 | **Render in `<iframe sandbox="allow-same-origin allow-popups allow-popups-to-escape-sandbox" srcdoc>`**, never in the app's own DOM. No `allow-scripts`, `allow-forms`, `allow-top-navigation`, `allow-modals`, `allow-downloads`. `referrerpolicy="no-referrer"`. | The sandbox is the primary containment: without `allow-scripts` nothing in the frame can run — no `<script>`, no handler, no `javascript:` URL, no plugin — whatever the sanitizer missed. `allow-popups` + `allow-popups-to-escape-sandbox` only let a clicked link open a normal tab (with `rel="noopener noreferrer"`). |
| D2 | **`allow-same-origin` is set, deliberately.** | It is dangerous only together with `allow-scripts` (a script could then remove its own sandbox); with scripts off, the frame's content is inert HTML and CSS. It is needed for two things: (1) the app measures the document for auto-height and zoom-to-fit (an opaque-origin frame cannot be read by the parent, and a scriptless frame cannot report its own size); (2) the frame's image requests to our own endpoints are then `Sec-Fetch-Site: same-origin`. Checked in Chromium on this host: without it every image request from the frame arrives as `cross-site` and `localhostGuard` refuses it — and relaxing the guard for images would let any web page the owner visits probe `/api/gmail/messages/…` through `<img>` load/error timing. With it, the guard stays as strict as it is. |
| D3 | **`srcdoc`, not a same-origin endpoint with a `Content-Security-Policy: sandbox` header.** | A CSP `sandbox` document has an opaque origin too (same problem as D2 for measuring and for the guard), it would need its own cached endpoint for the HTML, and a top-level visit to that URL would render the mail outside the reader. `srcdoc` keeps the HTML in the JSON answer of the reader's request, inherits the app's CSP (policy container of `about:srcdoc`) **and** carries its own (D5). |
| D4 | **Sanitize on the server with an allowlist: sanitize-html 2.18.0** (htmlparser2 12.0.0, postcss 8.5.28, all pinned exactly, every package of the install published ≥ 14 days before 2026-10-15, installed with `npm install --before=2026-10-01`). | A maintained allowlist sanitizer with a long security history. 2.18.1 (published 2026-10-14) fixes GHSA-c9rx-x947-fp3h, a denial of service through nested discarded `<iframe>` fallback markup re-sanitized recursively; it is one day old, so 2.18.0 is pinned and the vulnerable path is made unreachable: `iframe` is in `nonTextTags` (its text is dropped, never re-sanitized). A test feeds 5,000 nested `<iframe>`s. |
| D5 | **The frame carries its own CSP** as the first element of its `<head>`: `default-src 'none'; script-src 'none'; object-src 'none'; img-src 'self' data:; style-src 'unsafe-inline'; font-src 'none'; media-src 'none'; frame-src 'none'; child-src 'none'; worker-src 'none'; connect-src 'none'; manifest-src 'none'; form-action 'none'; base-uri 'none'`, plus `<meta name="referrer" content="no-referrer">`. The app's own CSP is **unchanged** (`frame-src` falls back to `default-src 'self'`, which admits `about:srcdoc`). | Defence in depth: even if markup survived the sanitizer and the sandbox somehow allowed it, nothing could load except our own same-origin URLs and `data:` images. `frame-ancestors`, `sandbox` and `report-uri` are not used in the meta policy (browsers ignore them there and print console errors). `'self'` resolves to the app origin because of D2 (checked in Chromium). |
| D6 | **The sanitizer's output must be a fixpoint.** It is sanitized again in a verify mode that accepts only the URLs the first pass wrote; if that changes anything, one more round is allowed (sloppy markup such as a stray `</p>` settles), and if it still changes, the reader shows the plain text (`reason: "unsafe"`). | Mutation XSS lives in markup that two parsers (or one parser twice) read differently. The output also never contains a raw-text element (`style`, `script`, `textarea`, `title`, `xmp`, `noscript`, `iframe`, `noembed`, `noframes`, `plaintext`), foreign content (`svg`, `math`), comments, CDATA or processing instructions, so the browser has nothing to re-interpret: every `<` in text is escaped and every attribute is quoted and escaped. |
| D7 | **CSS is kept (newsletters need it) but rebuilt, not passed through**: `<style>` text is read separately with htmlparser2 and rebuilt from a postcss parse with only plain rules and `@media`; declarations are judged after CSS escapes are decoded and comments removed; only an allowlist of CSS functions survives, judged with strings blanked the way CSS tokenizes them (an escaped quote is not a string, so `\"x foo(1) \"` cannot hide `foo(`); every `url()` becomes our same-origin URL or `none`. **Every scan is linear**: numbers are read by a hand-written tokenizer (sign, digits, fraction, exponent, unit; more than 12 digits drops the declaration), never by a backtracking regex. | `<style>` is the classic way around HTML sanitizers (`@import`, `url()`, `expression()`, `behavior`, `-moz-binding`, escape tricks such as `u\72l(`, `@\69mport`, comment splits such as `ur/**/l(`). Rebuilding from a parse and escaping `<` means the CSS can never close its `<style>`. The review found `/(\d*\.?\d+)(px|…)/g` backtracking cubically on a digit run: ten 2,000-digit `width`s (20 KB) held the event loop for 47 s; the same mail now sanitizes in milliseconds (tests: 2,000 digits in a declaration, an attribute, a `<style>` and a megabyte of them). |
| D8 | **Remote images are never loaded until asked, and then only through the server.** The body endpoint writes no remote URL at all while images are blocked (the `<img>` keeps its alt text and size as an empty box); with images allowed it writes `/api/mail-images/proxy?m=<messageId>&u=<url>&s=<sig>`. | The sender learns nothing from an unopened image: not that the mail was opened, not the owner's IP, device, browser or cookies. After 顯示圖片 the sender sees the server's requests (a generic `User-Agent: Mozilla/5.0`, no Referer, no cookies), all at once when the body is built (D19): it learns **that and when the mail was opened, and the server's network address** — not the owner's device, browser, screen, system settings or what the owner hovers or clicks. BELL Personal is self-hosted: its requests leave from the owner's own connection (at home, the same public IP the browser would have used; when reading remotely over Tailscale, the home IP instead of the phone's). The copy says exactly that (「寄件者看不到你的裝置或瀏覽器，但會看到伺服器的 IP 位址」); it never claims to hide the IP. Hiding it needs an egress proxy (§11). |
| D9 | **The proxy is not an open proxy:** `s` is HMAC-SHA-256 over `messageId + "\n" + url` with a **random 32-byte key generated per process** (`ImageSigner`), checked with `timingSafeEqual`. | Only URLs the body endpoint wrote for that message can be fetched. A per-process key needs no storage and never leaves memory; a restart invalidates old URLs, and the reader simply asks for the body again. Deriving it from the master key was rejected: it would tie a second secret to the vault key for no benefit (signatures never need to survive a restart). |
| D10 | **SSRF guard for every proxy fetch (`server/public-fetch.ts`).** http/https only, no credentials, default ports only; names that only mean something inside a network are refused before any lookup (`localhost`, `.local`, `.internal`, `.lan`, `.home.arpa`, `.arpa`, **`.ts.net`** (the tailnet), single labels, `.test`, `.example`, `.invalid`, `.onion`…); names are resolved with c-ares (a `dns.promises.Resolver` per lookup, A and AAAA, 2 s, one try, **cancelled** when the fetch's deadline passes — `dns.lookup` runs getaddrinfo on libuv's threadpool, where an abandoned lookup keeps its thread for the resolver's full timeout, so a mail naming 150 slow hosts starved every other outbound lookup for minutes); **every** address a name resolves to must be public unicast (refused: 0/8, 10/8, **100.64/10 (CGNAT: the tailnet)**, 127/8, 169.254/16 (incl. the metadata address), 172.16/12, 192.0.0/24, 192.0.2/24, 192.88.99/24, 192.168/16, 198.18/15, 198.51.100/24, 203.0.113/24, 224/4, 240/4; IPv6 outside 2000::/3, 2001::/23 (Teredo), 2001:db8::/32, 2002::/16 (6to4), 3fff::/20; IPv4-mapped IPv6 is judged by its IPv4); the connection is **pinned** to the checked address (node:http/https with a `lookup` that returns it), so DNS rebinding cannot move it; redirects are followed by hand, at most 3, each hop checked again; one 10 s deadline; a 10 MB cap counted on received bytes with `Accept-Encoding: identity`; no cookies, no Referer, generic UA. | The proxy fetches URLs a stranger chose. The WHATWG URL parser normalises `2130706433`, `0177.0.0.1`, `0x7f.1`, `127.1` and `[::ffff:127.0.0.1]` to their real address before the literal check. TLS still verifies the certificate for the URL's host name (SNI and the hostname check use it). |
| D11 | **Only raster images are ever served, recognised by magic bytes** (PNG, JPEG, GIF, WebP, AVIF), never by the sender's `Content-Type` or file name: SVG (which can carry script), HTML and everything else is 415. **And only with a decoded size the reader can afford** (`acceptableRaster`: both sides named in the header, each ≤ 16,384, ≤ 40 million pixels; a GIF's frames grow its canvas, AVIF's size is its largest `ispe`; an unknown size is refused) — for `cid:` parts and attachments (415), proxied images (413) and `data:` images (dropped). Responses carry the sniffed `Content-Type`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Content-Disposition: inline; filename="…"` (cleaned, with the sniffed type's extension), `Cache-Control: private, max-age=300`, `Cross-Origin-Resource-Policy: same-origin`. | An image URL opened in its own tab is still only an image, sandboxed, of this origin. A part labelled `image/png` that holds HTML is refused, and a GIF labelled PNG is served as what it is. A 64 KB PNG can declare 23000×23000 pixels; the review measured one such `data:` image taking the reader's tab from 440 MB to 3.1 GB, with no click (cid:/data: images are always shown, and the attachment strip renders in the app's own document). |
| D12 | **Inline `cid:` images and image attachments are served same-origin from Gmail**: `GET /api/gmail/messages/:id/inline/:contentId` and `GET /api/gmail/messages/:id/attachments/:partId`, bytes from `messages.attachments.get`. The attachment URL uses the MIME **part id**, not Gmail's attachment id. | Gmail issues a new attachment id on every read of a message, and the ids are long; the part id is stable. A held id that went stale is re-read once (tested with rotating ids). The Content-ID in the inline path can name the sender's domain (`part1.x@example.com`), so the request log writes it as 「…」 (`loggablePath`). |
| D13 | **Known tracking pixels are never loaded**: an `<img>` at most 1×1 (attributes or style), with a zero dimension, `display:none`, `visibility:hidden` or opacity 0, or on a known open-tracking host or endpoint (`server/features/gmail/trackers.ts`: list-manage.com, mandrillapp.com, ct.sendgrid.net, mailtrack.io, …, `/wf/open`, `/track/open.php`, `/open.aspx`) is removed by the sanitizer — also when images are shown — and counted (「已擋下 N 個追蹤像素」). The proxy checks every redirect hop against the same list before sending anything to it (`publicFetch` `checkUrl`): an image on the sender's own host that redirects to `ct.sendgrid.net/wf/open` stops there and the browser gets our transparent GIF. An image the proxy fetched that decodes to ≤ 1×1 is replaced by our own transparent GIF. | The main defence is D8 (nothing loads unasked); the list is a short, best-effort extra. A pixel recognised only by its decoded size, or the first hop of a redirecting one, **was** fetched: its bytes never reach the browser, but its request reached the sender. So the copy promises 「已知的追蹤像素不會載入」, never 「一律不載入」, and /privacy says that a pixel recognised after downloading has already been requested. |
| D14 | **HTML is read live and never stored**: `messages.get(format=full)` when the reader shows the message; decoded HTML, its parts and served images are held only in `LiveMail` (server memory, 5 minutes, LRU, bounded by bytes: 12 MB of bodies, 32 MB of images), dropped on 清除快取的信件, on disconnect and when an action changes the conversation. Never in `source_items`, the logs or backups. | decisions.md item 9 keeps its retention promise: the 30-day cache still holds only metadata and the ≤ 8 KB plain-text excerpt. |
| D15 | **Budgets**: decoded HTML ≤ 1,000,000 characters (else plain text, `too-large`); a message answer over the existing 5 MB cap falls back to its headers (plain text, `too-large`); CSS ≤ 200,000 characters; one style attribute ≤ 4,000; ≤ 40,000 style declarations per message; **the whole sanitizer job ≤ 3 s of wall clock** (checked per element, style and rule; past it the result is refused, `slow` → plain text `too-large`, log `gmail.body_slow`); `data:` images ≤ 256 KB each, 1 MB together; ≤ 200 distinct remote images; images ≤ 10 MB and ≤ 40 Mpx (D11); proxy: ≤ 6 fetches at once and **≤ 4 for one message** (a hostile mail's slow hosts always leave 2 slots to every other mail), **≤ 30 s waiting for a slot** (then `timeout`), one fetch per URL at a time, ≤ 150 upstream fetches per message and ≤ 600 overall per 5 minutes (429; a fetch that ends in a refusal gives its share of the overall budget back, so a hostile mail's failures cannot spend it for everyone). | Sanitizing runs on the event loop; a hostile mail must not hold it. Every scan is linear (D7) and the wall-clock budget bounds whatever is left. A 1 MB newsletter sanitizes in about 0.25 s on this host; 10,000 pixels, 30,000 `<style>` elements or a megabyte of 2,000-digit numbers stay linear (removed images become empty `<span>`s instead of being cut out of the output, which copied the output once per element). The review measured one hostile mail's 18 trickling images delaying another mail's image by 30 s; with the per-message cap the other mail starts at once. |
| D16 | **The trust list stores addresses or domains** (`mail.trustedImageSenders`, ≤ 200, lower-cased, validated). The notice's button trusts **the sender's address**, and names it (「一律顯示「newsletter@ithome.com.tw」的圖片」), never only a display name anyone can set; a domain (and its subdomains) is added in 資料與隱私. | A `From:` address can be forged. Trust only means "load this sender's remote images through the proxy without asking": known tracking pixels stay out, the owner's device and browser stay hidden, and the cost of a forged trusted sender is what D8 lists — the server's address and that (and when) the mail was opened. Because the server fetches every image of the body at once (D19), the mail's CSS cannot turn hover, screen width or the system's dark mode into requests. The settings hint says so: 「寄件者看不到你的裝置或瀏覽器，但會看到伺服器的 IP 位址，也會知道信被打開」. |
| D17 | **Logs carry counts and outcomes only**: `gmail.body {outcome, reason?, ms, chars, remote, trackers, inline, attachments, shown, trusted}`, `gmail.body_unstable {chars}`, `mail.image {source: remote\|inline\|attachment, outcome, ms, bytes?}`. Never a URL, host, subject, sender or Content-ID. | ARCHITECTURE §9 logging rule; tested by capturing stdout. |
| D18 | **The frame is sized to its content** (ResizeObserver on its body; the height is the content's own — the root's box and what sticks out below the body (`contentHeight`), never `documentElement.scrollHeight`, which cannot drop below the frame's current height, so the frame grows and shrinks; `HeightGuard` freezes it after 200 changes or past 30,000 px, then the mail scrolls inside), **zoomed to fit** a fixed-width mail down to 0.5 (CSS `zoom` on the frame's root; wider mail scrolls sideways inside the frame, never the page), and shown on a **white paper card in both themes** (most mail assumes a white page) with the app's chrome around it. **The paper stays light whatever the owner's system uses**: `color-scheme` (and `supported-color-schemes`) is dropped from the mail's CSS, `@media` queries on `prefers-color-scheme` are settled as light (`(prefers-color-scheme: light)` is taken out as always true; a query that tests the scheme any other way — dark, `not`, `or`, no value — is dropped as never true), and `html:root{color-scheme:light only!important}` comes after the mail's CSS. | The sanitizer removes what makes a page depend on its frame's height (viewport units; `height:100%` on html/body is overridden after the mail's CSS), and the guard stops whatever is left. Media queries inside the frame see its width, so responsive newsletters adapt by themselves. Inside a frame, `prefers-color-scheme` follows the owner's system, not the frame element's `color-scheme`: a Litmus-style `:root{color-scheme:light dark}` turned the page dark (white text) on the white card, and half-done dark rules made text unreadable. |
| D19 | **The server decides what is fetched and when.** When the body endpoint builds a body with images shown, it starts `ImageProxy.prefetch` of **every** remote image in it (in the mail's order, under the budgets of D15). The proxy route answers the browser **only** from that fetch: the held image, a held refusal, or the fetch still in flight; a signed URL whose fetch is not held (5 minutes, the 32 MB image cache, 清除快取的信件) is 410, never fetched again because the browser asked. | Otherwise the browser decides: with images on, `url()` inside `:hover`, `:active`, `@media (pointer:coarse)`, `(max-width:480px)` or `(prefers-color-scheme: dark)` is requested only when it matches, so the sender learned the device class, viewport width and live hover events (reproduced in Chromium by the review). Dropping `url()` from such rules would not be enough: an unconditional background on an element that a media query hides is also fetched or not depending on the screen. Fetching everything up front (like Apple Mail Privacy Protection) makes the set and timing of upstream requests independent of the client. Cost: images the owner never sees (another device's variant, a hover image) are fetched too, within the same budgets. |
| D20 | **The only tooltip is the real destination.** `title` is no longer a global attribute: only a link carries one, ours (「連到 {host}」 / 「寄信給 {address}」); a `mailto:` whose address holds a format or control character (bidi overrides such as U+202E, zero-width characters) is no link at all; a link without a usable target (`#anchor`, `tel:`, `javascript:`, relative) becomes a plain `<span>` that keeps its own style, so it no longer looks clickable. The mail's `<html dir lang>` (checked values) is written on the frame's wrapper. | Browsers show the innermost element's title: `<a href="https://evil.example"><span title="連到 www.esunbank.com.tw">` showed the app's own wording for a host the click did not go to. A U+202E inside a mailto address reversed the tooltip into a different address. RTL mail that sets `dir` only on `<html>` (most Arabic and Hebrew mail) lost its direction, and `lang` on `<html>` picks CJK glyphs. |
| D21 | **Keys inside the frame never take over a link**: Enter and Space on a focused link stay with the link (it opens); every other key still reaches the app's dispatcher (`forwardsKey`). After 顯示圖片 or 一律顯示 from the notice, focus moves to the note that replaces it (never `<body>`); a failed image load keeps the blocked layout with 「外部圖片沒有載入：{reason}」 [重試], and 顯示圖片 or `I` ask again. The reader keeps a held answer with proxied images for 5 minutes only (the server's own window, D19), then asks for the body again. | The forwarded copy of Enter targeted `window`, so the reader's ↵ ran the conversation's first action (封存) and cancelled the link. A failed `?images=1` left a 顯示圖片 that did nothing. A held body outliving a server restart showed broken images with no way back. |

## 1. Flow

```
reader opens a message (原始版面)
  └─ GET /api/gmail/messages/:id/body[?images=1] ─► messages.get(format=full)  (live; LiveMail 5 min)
        ├─ no HTML / too big / not connected / unstable ─► {kind:"text", reason} → the cached plain text (+ note)
        └─ sanitize (sanitize-html allowlist + CSS rebuild + URL policy + tracker removal) ─► fixpoint check
              └─ {kind:"html", document, images:{remote, shown, trusted, trackers}, sender, attachments}
                   ├─ images shown: ImageProxy.prefetch(every remote URL) ─► publicFetch (SSRF guard, pinned, tracker hops refused)
                   │                                                        → raster + decoded-size check → pixel → transparent GIF
                   └─ <iframe sandbox srcdoc=document>   (frame CSP + app CSP; no scripts)
                        ├─ cid:            → GET /api/gmail/messages/:id/inline/:contentId ─► attachments.get → raster + size check
                        ├─ remote (asked)  → GET /api/mail-images/proxy?m&u&s ─► HMAC check → the prefetch's answer (held / in flight / refused; else 410)
                        └─ links           → new tab, noopener noreferrer
  image attachments strip → GET /api/gmail/messages/:id/attachments/:partId
```

## 2. Fetching (requirement A)

- `readMailBody()` (`server/features/gmail/mail-body.ts`): `messages.get(format=full)` through the existing `GmailApi` (safeFetch: HTTPS, no redirects, 15 s, **5 MB** cap). Over the cap: `format=metadata` for the sender, `htmlTooLarge`. The first `text/html` part that is not an attachment is the body; when Gmail left it out of the answer (`attachmentId`), one `attachments.get` capped at 4 MB.
- Decoding: `decodeBytes()` — the plain-text path's rules (valid UTF-8 wins, else the declared charset such as Big5, 7-bit ISO-2022 first when it has escapes). Over 1,000,000 characters → `too-large`.
- Image parts: every `image/*` part (and `application/octet-stream` with an image file name) except `image/svg+xml`, with part id, Content-ID (or `X-Attachment-Id`), file name, size, disposition. A part listed as an attachment is shown in the strip unless the HTML shows it inline.
- Memory only (D14). Without Gmail (not connected or reconnect needed) the body answers `{kind: "text", reason: "not-connected"}` and the image endpoints 503.

## 3. Sanitization (requirement B)

### 3.1 Elements

- **Kept** (content and tag): `a abbr address article aside b bdi bdo big blockquote br caption center cite code col colgroup dd del dfn div dl dt em figcaption figure font footer h1–h6 header hgroup hr i img ins kbd li main mark nav ol p pre q s samp section small span strike strong sub sup table tbody td tfoot th thead time tr tt u ul var wbr`. A mail's `<body>` becomes a `<div>` (its `bgcolor` and `background` become CSS).
- **Dropped with their content**: `script style textarea option select datalist xmp noscript iframe frame frameset noframes noembed plaintext title template svg math object applet embed audio video canvas` (raw-text and foreign content: what htmlparser2 reads inside is not what a browser reads).
- **Dropped, content kept**: everything else (`html head body meta link base form input button picture source marquee …`). `<html>`'s checked `dir` and `lang` go on the frame's wrapper (D20).
- `nestingLimit` 200.

### 3.2 Attributes and URLs

- Global: `id class dir lang align style` (no `title`: D20); per tag: `a: href target rel title` (ours only); `img: src alt width height border hspace vspace`; tables: `width height border cellpadding cellspacing bgcolor background valign colspan rowspan nowrap span`; `font: color face size`; `hr: width size color noshade`; `ol: start type`; `ul: type`; `li: type value`; `time: datetime`. Values are checked (numbers capped at 5000 px / 100 %, colours, enums); anything else is dropped — every `on*`, `srcset`, `sizes`, `formaction`, `xlink:href`, `ping`, `data-*`, `poster`, `usemap`.
- **Links**: absolute `http:`, `https:`, `mailto:` only (≤ 4000 characters, no `user:pass@`; a mailto address with a format or control character such as U+202E is refused), rewritten with `target="_blank" rel="noopener noreferrer"` and `title="連到 {host}"` (`寄信給 {address}` for mailto): the real host, punycode for IDN — the only `title` in the output. Relative, fragment, protocol-relative, `tel:`, `javascript:`, `vbscript:`, `data:` links become a plain `<span>` with the link's own style (no link colour, nothing to click).
- **Images** (`img src`, table `background`, CSS `url()`): `cid:` → this message's inline part (Content-ID matched exactly, else case-insensitively; unknown → dropped); `data:image/(png|jpeg|gif|webp);base64` only when the bytes sniff as the declared type with a sane decoded size (D11), ≤ 256 KB each, ≤ 1 MB together; absolute `http(s)` without credentials or a port → the proxy when images are allowed, else nothing (the `<img>` keeps alt and size); everything else → dropped (an `<img>` with nothing to show and no alt is removed).

### 3.3 CSS

- `<style>`: plain rules and `@media` (params `[a-z0-9 (),:./-]`, no `url`) only; `@import`, `@font-face`, `@namespace`, `@keyframes`, `@supports`, `@layer`, `@page`, `@-moz-document`, `@charset`… dropped; nested rules dropped; selectors ≤ 500 characters, no `{ } ; < @`, parentheses ≤ 4 deep; a block that does not parse is dropped whole; `<` in the output becomes `\3c `.
- Declarations (style blocks and `style` attributes): property `^-?[a-z][a-z0-9-]*$` after decoding (custom properties dropped), not `behavior`, `-ms-behavior`, `-moz-binding`, `binding`, `src`, `-o-link*`, `user-modify`, `color-scheme`, `supported-color-schemes`; value ≤ 2000 characters with no `{ } ; < > @`; checked **after decoding escapes and removing comments**: no `expression( image-set( image( cross-fade( element( paint( src( var( attr( env( javascript: vbscript: progid: -moz-binding @import`, no backslash left, no control characters; only these functions (strings blanked first, escape-aware): colour functions, `calc min max clamp`, gradients, 2-D transforms (`translate*`, `scale*`, `rotate`, `skew*`; no 3-D transforms, `matrix*` or `perspective()`, which magnify without a size in the value), `cubic-bezier steps rect inset circle ellipse polygon`, filter functions, `counter(s) repeat minmax fit-content`; `position` static or relative only (no `fixed`, `sticky`, `absolute` overlays inside the frame); no viewport units; **sizes** (`sizesWithinCaps`, one linear pass): every number read whole with its exponent (`1e9px` is a billion pixels; more than 12 digits drops it), the declaration's lengths added up against their caps (≤ 5000 px and equivalents in total; corner radii are not counted, so `border-radius: 9999px` pill buttons stay), times what `*` and `/` inside `calc() min() max() clamp()` and `repeat()`'s count can multiply them by (an operator without a plain number beside it drops the declaration); unitless multipliers (`zoom`, `line-height`, `scale`, `scale*()`) ≤ 10, `tab-size` ≤ 16. Best effort: nesting (`font-size: 200em` inside another) still compounds, and the frame's own guards (D18: the 30,000 px height cap, sideways scrolling inside the frame at ≥ 0.5 zoom) are the real bound on what a mail can draw. `url()` rewritten as in §3.2 (an escaped `url()` is dropped, never rewritten).
- `@media` on `prefers-color-scheme` is settled as light (D18): `(prefers-color-scheme: light)` is taken out of its query (`@media all` when nothing is left), any other test of the scheme drops that query, and a block with no query left is dropped.
- Frame page (`mailDocument`): base CSS in system colours (`Canvas`, `CanvasText`, `LinkText` for `a[href]`, `GrayText`, `color-scheme: light`: a white page with no hex colour), `img{max-width:100%;height:auto}`; then the mail's CSS; then overrides (`html:root{color-scheme:light only!important}`, `html:root, html:root>body {height:auto!important; min-height:0!important; position:static!important}`, horizontal overflow scrolls inside); the wrapper `<div class="bell-mail" dir lang>` carries the mail's `<html>` direction and language.

- English summary: "…show a message's original layout only when the owner opens them…" and "When the owner opens a message, its HTML and inline images are read from Gmail on demand, filtered on the server, shown in a sandboxed frame that cannot run scripts, and kept only in server memory for up to five minutes; HTML is never stored. Remote images are not loaded unless the owner asks or trusts the sender; they are then fetched by the owner's server, never by the browser, all at once when the message is opened, so the sender sees the server's network address (usually the owner's own connection) and when the message was opened, but not the owner's device, browser or cookies; they are kept in memory for up to five minutes, and known tracking pixels are not loaded."

## 11. Known limits

- Not verified against a live Gmail account: `format=full` answers with real MIME trees, attachment-id rotation (emulated in the fake), Big5/ISO-2022 HTML parts from real senders.
- The proxy follows only default ports and http(s); an image on `:8080` stays broken. AVIF without an `ispe` box (some image sequences) is refused.
- The sender sees the server's IP address, which for a self-hosted server is the owner's own connection (D8). Hiding it would need an egress proxy (a setting naming an HTTP CONNECT or SOCKS proxy that `pinnedRequest` tunnels through, with the claim made only while one is set); not built.
- Images the server fetched for a body are answered for 5 minutes, while the 32 MB image cache holds them: a mail whose images exceed it, or a hover after five minutes, shows a broken image rather than fetching again because the browser asked (D19). The reader asks for the body again after five minutes.
- The CSS size cap is best effort (§3.3); the frame's guards bound what is left.
- Sanitized output is not cached: each open (and 顯示圖片) sanitizes again, which is linear and bounded by the 3 s budget.
- A mail whose `<style>` does not parse as a whole (an unclosed block, `@\69mport`) loses all of that block's CSS; a browser would have kept part of it.
- Images in older messages of a conversation load only when the message is opened; `I` acts on the newest message.
- A refused proxy image (private host, too large, not an image) shows as a broken image and the browser logs the failed request in the console; that comes from the mail's content, not the app.
- The tracker list is best effort; the real guarantee is that nothing remote loads without the owner's click (or trust).
